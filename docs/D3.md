# D3 — полное описание `appeals-analyzer`

## 1. Назначение документа

Этот документ описывает навык `appeals-analyzer` (далее — D3) в двух
независимых runtime:

- `production` — анализ обращений в закрытом корпоративном контуре;
- `testing` — облегчённый внешний runtime на синтетическом наборе.

Описание не содержит реальных обращений, клиентских данных, диалогов,
production connection strings, API-ключей, названий внутренних подразделений
или реальных идентификаторов. Для примеров используются только ID вида
`APPEAL-TEST-*` и нейтральные синтетические тексты.

## 2. Назначение D3

Production D3 предназначен для поиска и анализа обращений по сочетанию:

- продуктовых фильтров;
- субпродуктовых фильтров;
- каналов;
- периода;
- смыслового запроса пользователя.

Он выполняет структурный prefilter, hybrid retrieval, гидратацию полных строк,
reranking, генерацию отчёта и поддерживает follow-up по найденной выборке.

Testing D3 сохраняет основной UX:

- применяет те же логические frontend filters;
- ищет по коротким синтетическим обращениям;
- валидирует выбранные LLM идентификаторы;
- возвращает количество, summary, evidence и гипотезы;
- сохраняет session state;
- отвечает на запрос по конкретному `APPEAL-TEST-*` из предыдущей выборки.

## 3. Положение в архитектуре

```text
Audit-Workstation
    ↓ сообщение пользователя
PostgreSQL message bus
    ↓ chat_id / media / metadata
nanobot PostgresChannel
    ↓ RuntimePatcher + ToolRegistry
workspace/tools/appeals_analyzer.py
    ↓ NANOBOT_SKILLS_RUNTIME
    ├── production → scripts/appeals_reports.py
    └── testing    → testing/runner.py
```

Bridge и frontend не получают специальных условий для testing. Имя Tool и
транспортный contract остаются прежними.

## 4. Runtime switch

Общий helper:

```text
lib/services/skill_runtime_mode.py
```

| Значение | Режим |
|---|---|
| отсутствует | production |
| пустое | production |
| `production` | production |
| `testing` | testing |
| иное | ошибка |

Не допускается `try production → except testing`. Ошибка production retrieval
должна быть видимой, а не маскироваться результатом на synthetic data.

Лог запуска:

```text
[appeals-analyzer] runtime=production
```

или:

```text
[appeals-analyzer] runtime=testing
```

## 5. Native Tool adapter

Основной adapter:

```text
workspace/tools/appeals_analyzer.py
```

`AppealsAnalyzerTool` следует Tool architecture 2.5.2:

- `Tool.enabled(ctx)`;
- `Tool.create(ctx)`;
- конфигурация `gateway.appeals_analyzer`;
- регистрация через текущий RuntimePatcher;
- lazy loading тяжёлого production stack;
- отдельный namespace production package для защиты от конфликтов импортов.

### 5.1. Параметры

| Параметр | Тип | Назначение |
|---|---|---|
| `prompt` | `string` | Полный исходный запрос пользователя |
| `session_id` | `string` | Ключ выборки и follow-up |

Для нового production-анализа prompt может быть canonical structured request
или legacy CSV-контрактом из четырёх полей:

```text
"продукты", "субпродукты", "каналы", "смысловой запрос"
```

Внутри активной сессии допускается обычная фраза follow-up.

### 5.2. Session resolution

Adapter использует request-scoped session key nanobot. Для PostgreSQL-канала:

```text
postgres:<conversation UUID>
```

Переданный моделью `webui_session` не должен объединять разные frontend
conversation: при наличии реального request context используется именно он.

### 5.3. Production namespace isolation

Production skill имеет собственный package namespace, создаваемый через
`importlib.util.spec_from_file_location`. Это необходимо, потому что в общей
процессной среде существуют top-level модули с похожими именами.

Перед загрузкой production runner adapter проверяет, что `utils.db` разрешён
именно в shared `workspace/utils/db.py`. Testing branch проходит до этой
проверки и поэтому не импортирует production DB stack.

## 6. Production runtime

### 6.1. Главный orchestrator

```text
workspace/skills/appeals-analyzer/scripts/appeals_reports.py
```

Точка входа:

```python
run_appeals_report(session_id, user_prompt="", filters=None)
```

### 6.2. Production flow

```text
полный пользовательский prompt
    ↓
есть активная session selection?
    ├── да и intent != NEW_SEARCH → follow-up pipeline
    └── нет / новый поиск
          ↓
parse_structured_analytical_request
          ↓
products / subproducts / channels / query / date_range
          ↓
структурный SQL prefilter → allowed IDs
          ↓
FAISS + BM25 hybrid retrieval по разрешённой популяции
          ↓
RRF fusion
          ↓
Greenplum hydration полных данных по найденным ID
          ↓
BGE reranker
          ↓
threshold или контролируемый fallback selection
          ↓
deduplication
          ↓
CSV/XLSX export
          ↓
малый session index + session extract
          ↓
narrative / hypotheses / evidence
```

## 7. Production request contract

Parser находится в:

```text
workspace/skills/appeals-analyzer/utils/greenplum_engine.py
```

Он поддерживает:

- canonical human-readable envelope;
- структурированный JSON-контракт;
- legacy четыре CSV-поля;
- exact canonicalization product/subproduct/channel;
- явный `date_range` для WEB JSON;
- контролируемое извлечение периода из semantic query для legacy CSV.

### 7.1. Product filters

Canonical допустимые значения читаются из:

```text
workspace/skills/appeals-analyzer/canonical_filters.json
```

В этом документе сами закрытые production-значения не перечисляются.

Фильтры не являются semantic пожеланием: production parser приводит их к
каноническим значениям, проверяет формат и применяет до semantic retrieval.

### 7.2. Date range

`validate_date_range()` принимает только пару ISO-дат `YYYY-MM-DD`, проверяет
реальность дат и порядок начала/конца.

Для structured WEB contract период является явным полем. Для legacy CSV
`extract_search_params()` пытается получить только `date_range`, не переписывая
исходный semantic query. Если LLM extraction невалиден, применяется узкий
детерминированный fallback по указанному году.

## 8. Production structural filtering

Модуль:

```text
workspace/skills/appeals-analyzer/utils/greenplum_engine.py
```

Отвечает за две разные стадии.

### 8.1. Candidate ID prefilter

`fetch_candidate_ids_by_product()`:

- выбирает допустимые временные секции;
- применяет продукт, субпродукт, канал и период;
- возвращает только ID кандидатов;
- не гидратирует все тяжёлые текстовые поля до semantic search.

Это уменьшает candidate population и не позволяет semantic retrieval выйти за
явные frontend-фильтры.

### 8.2. Hydration

`fetch_appeals_by_ids()` получает полные данные только для ID, прошедших
retrieval. Внутри:

- базовые строки группируются по временным секциям;
- отдельно загружаются связанные диалоги и задачи;
- колонки приводятся к единой логической схеме;
- фрагменты связанных текстов объединяются;
- строки дедуплицируются;
- технические различия источников скрываются от верхнего pipeline.

Точные production schema/table names и реальные данные здесь намеренно не
публикуются.

## 9. Production hybrid retrieval

Модуль:

```text
workspace/skills/appeals-analyzer/utils/bge_search_engine.py
```

### 9.1. Компоненты

- BGE embedding model;
- FAISS dense index;
- BM25 sparse shards;
- RRF fusion;
- BGE cross-encoder reranker;
- metadata и date mask;
- optional multi-device execution;
- контроль доступной GPU memory;
- управляемый CPU fallback для отдельных model operations.

### 9.2. Integrity checks

Перед поиском проверяются:

- наличие metadata;
- соответствие числа doc IDs размеру FAISS index;
- корректность диапазонов BM25 shards;
- отсутствие gap/overlap;
- покрытие всей коллекции;
- существование локальных моделей;
- допустимые compute devices.

Нарушение integrity не должно превращаться в правдоподобный пустой отчёт.

### 9.3. Allowed mask

`build_allowed_mask()` ограничивает semantic corpus:

- ID из product prefilter;
- допустимым периодом;
- пересечением этих условий.

### 9.4. Hybrid retrieval

`retrieve_hybrid_adaptive()` выполняет:

1. dense retrieval по FAISS;
2. sparse retrieval по BM25;
3. сохранение лучшего ранга каждого ID;
4. RRF fusion;
5. возврат ограниченного списка существующих ID.

### 9.5. Reranking

После hydration `rerank_dataframe()` оценивает пары query/document.

`select_threshold_or_fallback()`:

- выбирает записи выше configured threshold;
- если threshold не прошла ни одна запись, использует явно отмеченный
  контролируемый fallback, а не скрытую подмену данных;
- передаёт признак fallback в session metadata.

## 12. Production sessions и follow-up

### 12.1. Session extract

```text
workspace/skills/appeals-analyzer/utils/session_extract_manager.py
```

Для каждого `session_id` хранится одна активная выборка:

- DataFrame найденных обращений;
- `id_to_text_map`;
- предыдущий narrative/hypothesis;
- export metadata;
- признак threshold fallback.

Новый поиск очищает предыдущий малый индекс и заменяет session extract.

### 12.2. Малый session index

`build_and_cache_small_index()` строит индекс только для текущей выборки.

`search_small_index()` используется для follow-up. При недоступности локальной
embedding model production код допускает явно логируемый degraded lexical
режим для session follow-up; это не внешний testing runtime.

### 12.3. Follow-up routing

```text
workspace/skills/appeals-analyzer/utils/intent_router.py
```

Intent различает:

- новый поиск;
- вопрос по конкретной записи;
- semantic search по текущей выборке;
- вопрос по готовому отчёту/гипотезам.

В `_run_follow_up()`:

1. Точный ID из prompt ищется в `id_to_text_map`.
2. Search intent идёт в session index.
3. Иначе формируется диалоговый ответ по сохранённому narrative.

## 13. Production export

`export_complaints_excel()` создаёт два файла:

- CSV UTF-8;
- XLSX с листом `appeals`.

Путь:

```text
workspace/skills/appeals-analyzer/data_store/generated_files/
```

Перед записью:

- `None` и `NaN` заменяются пустыми значениями;
- collections сериализуются в JSON;
- удаляются недопустимые Excel control characters;
- строка ограничивается пределом Excel cell;
- результат дедуплицируется по ID.

Пользовательский ответ содержит narrative и путь к XLSX с количеством
уникальных записей.

## 14. Production empty/error paths

Функция `_empty()`:

- очищает session semantic index;
- сохраняет пустой DataFrame для данной session;
- сохраняет поясняющее сообщение;
- возвращает понятный текст вместо traceback.

Отдельные причины:

- invalid structured request;
- отсутствуют строки после product filter;
- hybrid retrieval недоступен;
- нет ID после retrieval;
- hydration не вернула данные;
- reranker недоступен;
- итоговая выборка пуста.

Production ошибка не активирует testing runtime.

## 15. Production delivery contract

`SKILL.md` содержит:

```text
FINAL_DELIVERY_MODE: APPEALS_REPORT_VERBATIM_V1
```

После успешного вызова report является готовым ответом. Nanobot не должен:

- сокращать список evidence;
- переписывать summary;
- удалять гипотезы;
- менять числа и relevance scores;
- заменять полный отчёт собственным резюме;
- терять пути к выгрузкам.

## 18. Testing parsing и filters

`testing/runner.py::_parse_request()` поддерживает тот же legacy CSV UX:

```text
"prd", "s_prd", "chnl", "semantic query"
```

Если четыре поля не распознаны, весь prompt считается semantic query без
структурных фильтров.

`apply_filters()` выполняет без LLM:

- exact case-insensitive filter по `prd`;
- exact case-insensitive filter по `s_prd`;
- exact case-insensitive filter по `chnl`;
- нижнюю границу `date_from`;
- верхнюю границу `date_to`.

Фильтры применяются до semantic selection.

## 19. Testing relevance search

Модуль:

```text
testing/llm_search.py
```

### 19.1. Lexical shortlist

`shortlist()`:

1. Нормализует query в слова длиной от четырёх символов.
2. Считает число вхождений в объединённые поля synthetic appeal.
3. Сортирует по score и ID.
4. Оставляет не более 60 кандидатов.

Если нет положительных lexical совпадений, используется первые 60 записей в
стабильном порядке, чтобы LLM мог оценить смысловую близость.

### 19.2. LLM batches

`search()` разбивает shortlist на batches по 25 записей. LLM получает только:

- synthetic ID;
- product/subproduct/channel;
- короткий synthetic text;
- пользовательский query.

Ожидаемый структурированный ответ:

```json
{
  "results": [
    {
      "id": "APPEAL-TEST-001",
      "score": 0.9,
      "reason": "Краткое обоснование релевантности"
    }
  ]
}
```

### 19.3. Защита от hallucinated IDs

`validate_results()`:

- принимает только объекты;
- проверяет `id in candidate_ids` текущего batch;
- удаляет дубликаты;
- ограничивает score диапазоном `0..1`;
- ограничивает длину reason;
- отбрасывает придуманные ID.

После объединения batches результаты сортируются по score и ID; возвращается
не более 50 записей.

## 20. Shared external LLM

Testing D3 вызывает только:

```text
lib.services.llm_client.call_llm_json
```

Конфигурация автоматически берётся из текущего nanobot:

- provider;
- model;
- apiBase;

Testing не содержит собственного API key, не вызывает corporate adapter и не

## 21. Testing report

Модуль:

```text
testing/report.py
```

Отчёт содержит:

- исходный semantic query;
- количество найденных обращений;
- summary происхождения результата;
- список evidence;
- для каждой evidence-записи: ID, дата, классификация, канал, score, synthetic
  text и reason;
- несколько гипотез;
- явную связь гипотез с evidence IDs.

Если relevant rows нет, отчёт явно сообщает об отсутствии результатов и не
формирует гипотезы без evidence.

Testing XLSX сейчас не создаётся: это сознательно лёгкий runtime. Production
export не переиспользуется, чтобы не подтянуть pandas/Greenplum/hydration stack.

## 22. Testing sessions и follow-up

Состояние хранится в:

```text
workspace/data_store/cache/testing/appeals/sessions/<safe-session>.json
```

Формат:

```json
{
  "query": "обезличенный запрос",
  "selected_ids": ["APPEAL-TEST-001"]
}
```

Если follow-up содержит конкретный `APPEAL-TEST-*` и этот ID присутствует в
`selected_ids` текущей сессии, runner возвращает детальную карточку synthetic
appeal без нового глобального поиска.

ID из другой session или ID, которого не было в предыдущем результате, не
получает доступ к чужой сохранённой выборке.

## 27. Диагностика

### Tool загружает production BGE в testing

Проверить лог runtime и переменную окружения. В testing adapter должен перейти
в `testing/runner.py` до `_require_shared_db()` и production package loader.

### Нет результатов после filters

Проверить точное соответствие synthetic `prd/s_prd/chnl`. Filters являются
exact и не исправляются LLM.

### LLM возвращает придуманные ID

Они должны исчезнуть после `validate_results()`. Если такой ID виден в отчёте,
это нарушение security/grounding invariant.

### Follow-up не находит ID

Проверить:

- существовал ли ID в предыдущем результате;
- совпадает ли frontend conversation/session;
- создан ли session JSON;
- не был ли запущен новый поиск в той же session.

### Dataset отсутствует

`load_records()` вызывает `ensure_testing_data()`. При отсутствии файла он
создаётся автоматически. Для ручного восстановления используется `--force`.

### Production retrieval падает

Нельзя включать testing как fallback. Нужно диагностировать production cache,
локальные модели, backend connection и integrity indexes.

## 28. Инварианты сопровождения

1. Production — default.
2. Testing — только explicit opt-in.
3. Production и testing session stores разделены.
4. Testing data полностью synthetic.
5. Любой testing ID содержит `APPEAL-TEST-`.
6. Frontend filters применяются до LLM.
7. LLM не может добавить ID вне candidate batch.
8. Testing LLM вызывается только через shared client.
9. Testing не импортирует BGE/FAISS/BM25/Greenplum stack.
10. `workspace/utils/db.py` не изменяется.
11. Frontend request session имеет приоритет над `webui_session`.
12. Production report передаётся losslessly.
