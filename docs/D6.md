# D6 — полное описание `ior-analyzer`

## 1. Назначение документа

Этот документ описывает навык `ior-analyzer` (далее — D6) в двух режимах:

- `production` — штатный закрытый контур с корпоративными источниками данных,
  локальными аналитическими компонентами и production-отчётами;
- `testing` — изолированный внешний контур на полностью синтетических данных и
  общем LLM-клиенте nanobot.

Документ не содержит реальных событий операционного риска, фамилий, номеров
клиентов, счетов, production DSN, API-ключей, закрытых значений справочников или
примеров с внутренними данными. Все идентификаторы в примерах имеют явные
тестовые префиксы: `EVE-TEST-*` и `DRP-TEST-*`.

## 2. Что делает D6

`ior-analyzer` анализирует инциденты операционного риска (ИОР). Основные
возможности production-режима:

- выборка ИОР по периоду, идентификаторам и предметным атрибутам;
- стандартные отчёты по финансовым и нефинансовым последствиям;
- анализ возмещений;
- анализ удалённых ИОР и изменений статуса;
- сводный анализ за период;
- досье конкретного события;
- ad-hoc анализ по произвольным фильтрам;
- структурированный анализ с детерминированной статистикой;
- построение аналитических гипотез;
- выгрузка CSV/XLSX;
- уточняющие вопросы по результатам текущей сессии.

Testing-режим сохраняет пользовательский смысл навыка, но намеренно не
воспроизводит закрытую инфраструктуру. Он поддерживает:

- 1000 детерминированных синтетических ИОР;
- фильтры по `EVE-TEST-*`, `DRP-TEST-*` и датам;
- `count`, сумму и среднее финансовых потерь;
- сумму возмещений;
- лёгкий semantic search через общий LLM nanobot;
- follow-up по ранее выбранной сессионной выборке;
- Markdown-отчёт с evidence.

## 3. Положение в общей архитектуре

```text
Audit-Workstation
    ↓ user message / attachment
PostgreSQL message bus
    ↓ role=user, status=pending, chat_id=<conversation UUID>
audit_bridge / nanobot gateway
    ↓ ToolRegistry / RuntimePatcher
workspace/tools/ior_analyzer.py
    ↓ NANOBOT_SKILLS_RUNTIME
    ├── production → workspace/skills/ior-analyzer/scripts/ior_reports.py
    └── testing    → workspace/skills/ior-analyzer/testing/runner.py
```

Audit-Workstation и bridge не знают о существовании testing-ветки. Для них D6
остаётся обычным инструментом nanobot с тем же именем `ior_analyzer`.

## 4. Переключение runtime

Переключатель определён в:

```text
lib/services/skill_runtime_mode.py
```

Правила:

| Значение `NANOBOT_SKILLS_RUNTIME` | Результат |
|---|---|
| переменная отсутствует | `production` |
| пустое значение | `production` |
| `production` | `production` |
| `testing` | `testing` |
| любое другое значение | ошибка конфигурации |

Не существует автоматического fallback между production и testing. Ошибка
production-компонента не переключает D6 на синтетические данные.

При выполнении tool в журнале появляется одна запись уровня запуска:

```text
[ior-analyzer] runtime=production
```

или:

```text
[ior-analyzer] runtime=testing
```

## 5. Native Tool adapter

Основная интеграционная точка:

```text
workspace/tools/ior_analyzer.py
```

Класс `IORAnalyzerTool` использует актуальный контракт nanobot 2.5.2:

- наследуется от `Tool`;
- реализует `enabled(ctx)`;
- создаётся через `create(ctx)`;
- конфигурируется секцией `gateway.ior_analyzer`;
- регистрируется текущим `RuntimePatcher`/`ToolRegistry`;
- не возвращает старый механизм регистрации.

### 5.1. Параметры Tool

| Параметр | Тип | Назначение |
|---|---|---|
| `prompt` | `string` | Полный исходный запрос пользователя без пересказа |
| `preset` | `string/null` | Необязательный production-пресет |
| `session_id` | `string` | Ключ продолжения анализа |

`prompt` обязателен. Tool не должен получать сокращённую интерпретацию запроса:
production-логика сама определяет пресет, фильтры, период и intent.

### 5.2. Session key

Функция `current_tool_session_id()` сначала пытается получить настоящий
request-scoped ключ через `current_request_session_key()` nanobot.

В PostgreSQL-канале типичный ключ имеет вид:

```text
postgres:<conversation UUID>
```

Таким образом, разные frontend conversations не используют общий глобальный
`webui_session`. Значение `webui_session` остаётся fallback только для CLI,
ручного запуска и unit-тестов, где request context отсутствует.

### 5.3. Dispatch

Последовательность `execute()`:

1. Валидировать runtime flag.
2. Записать выбранный runtime в лог.
3. Разрешить настоящий session key.
4. Для testing лениво загрузить изолированный пакет `testing`.
5. Для production лениво загрузить существующий `run_ior_report`.
6. Передать полный `prompt`, `preset` и session key.
7. Вернуть уже сформированный отчёт.

## 6. Production runtime

### 6.1. Главная точка входа

```text
workspace/skills/ior-analyzer/scripts/ior_reports.py
```

Главная coroutine:

```python
run_ior_report(preset_name, session_id, user_prompt, filters=None)
```

Она координирует маршрутизацию, получение данных, нормализацию, расчёты,
экспорт, сессионный индекс и итоговый narrative.

### 6.2. Production flow

```text
полный prompt
    ↓
проверка structured-analysis envelope
    ├── да → scripts/analysis_mode/runner.py
    └── нет
         ↓
проверка follow-up по текущей сессии
    ├── конкретный EVE → точный поиск в session DataFrame
    ├── semantic follow-up → малый session index
    └── новый анализ
         ↓
определение preset + периода + предметных фильтров
         ↓
production data store
         ↓
SQL/preset query или dynamic read-only query
         ↓
DataFrame normalization / deduplication / aggregation
         ↓
CSV + XLSX
         ↓
session extract + session semantic index
         ↓
hypothesis narrative или deterministic graceful fallback
```

### 6.3. Выбор режима запроса

Production различает четыре смысловых режима.

#### Preset

Стандартный заранее описанный сценарий. Реестр production-пресетов находится в:

```text
workspace/skills/ior-analyzer/scripts/preset_analysis/registry.py
```

Поддерживаются:

- `financial_consequences_ior`;
- `deleted_ior`;
- `vozmeshenie_ior`;
- `ior_nonfinancial_consequences`;
- `ior_period_pao_sberbank`;
- `report_period_specific_ior`;
- `ior_hypothesis`;
- `credit_no_way_collect_debt` — legacy, только при явном выборе.

`report_period_specific_ior` допустим только для запроса с конкретным EVE-ID.
DRP/SBR, период, оргструктура, процессы и суммы являются ad-hoc фильтрами и не
должны ошибочно маршрутизироваться в досье одного события.

#### Ad-hoc

Функции `has_specific_codes`, `parse_period`, `ground_query` и
`build_dynamic_sql_from_prompt` определяют, нужен ли targeted read-only query.
Динамический запрос строится только по разрешённым таблицам и полям текущего
backend registry.

#### Follow-up

Если в session storage есть предыдущая выборка, production может:

- найти конкретное событие точным совпадением идентификатора;
- выполнить semantic search только по текущей выборке;
- сформировать уточняющий ответ по найденным описаниям.

#### Structured analysis

Parser расположен в:

```text
scripts/analysis_mode/parser.py
```

Исполнение:

```text
scripts/analysis_mode/runner.py
```

Подмодули:

| Модуль | Ответственность |
|---|---|
| `models.py` | Модели запроса, результата и ошибки валидации |
| `parser.py` | Canonical envelope/JSON parsing |
| `registry.py` | Допустимые виды анализа |
| `statistics.py` | Детерминированные показатели |
| `direct_loss.py` | Анализ прямых потерь |
| `anomalies.py` | Выбросы и аномальные наблюдения |
| `hypotheses.py` | Формирование гипотез |
| `report.py` | Сборка пользовательского результата |
| `export.py` | Управляемый XLSX-export |
| `runner.py` | Оркестрация режима |

Structured analysis нельзя одновременно запускать с внешним `preset` или
`filters`: это защищает от неоднозначной семантики.

## 7. Production data layer

Основной модуль:

```text
workspace/skills/ior-analyzer/utils/data_store.py
```

Он предоставляет единый интерфейс `query_sql()` и несколько явно выбираемых
backend-реализаций.

| Класс | Назначение |
|---|---|
| `NanobotCacheStore` | Штатное чтение опубликованного nanobot cache/snapshot |
| `GreenplumStore` | Явный production/diagnostic доступ к корпоративной БД |
| `SparkHiveStore` | Явный Spark/Hive backend |
| `LocalDuckDBStore` | Локальная диагностическая разработка |

Фабрика `get_data_store()` выбирает backend только из конфигурации. Между
backend нет неявного переключения после ошибки.

### 7.1. Важная граница БД

Shared connection layer:

```text
workspace/utils/db.py
```

не является частью D6 и не изменяется testing runtime. Production contract
подключения и connection pool сохраняются без модификации.

Исторический `workspace/skills/ior-analyzer/utils/db.py` остаётся внутри
production skill, но native adapter специально обеспечивает приоритет shared
`workspace/utils` namespace.

### 7.2. Логическая модель данных

Без раскрытия production-названий источников D6 работает с группами сущностей:

- основная карточка ИОР;
- история изменения статусов;
- финансовые последствия;
- нефинансовые последствия;
- возмещения;
- предметные классификаторы и оргструктура.

Типичные логические атрибуты:

- идентификатор события;
- код/направление риска;
- даты регистрации, начала и изменения статуса;
- статус;
- описание события;
- причина и последствия;
- сумма финансового воздействия;
- сумма возмещения;
- продукт, канал, бизнес-линия;
- технические идентификаторы detail-сущностей.

Реальные значения этих полей в документе намеренно не приводятся.

## 8. Нормализация и расчёты production

После получения DataFrame pipeline выполняет, в зависимости от пресета:

- вторичную точную фильтрацию периода;
- smart-filter по запросу;
- агрегацию detail-строк до уровня события;
- дедупликацию финансовых последствий или возмещений по собственным ID;
- преобразование технических заголовков в пользовательские;
- приведение денежных полей к числовому формату;
- подготовку безопасных значений для Excel;
- расчёт количества событий и сумм;
- построение top-наблюдений;
- расчёт распределений, концентраций и аналитических признаков;
- формирование гипотез и evidence.

Детерминированные показатели рассчитываются кодом. LLM не должен заменять
точную арифметику.

## 9. Production LLM и semantic search

### 9.1. LLM

Production D6 рассчитан на закрытый контур. Его исторический LLM adapter:

```text
workspace/skills/ior-analyzer/utils/local_qwen.py
```

используется для:

- классификации intent;
- подробного ответа по одному или нескольким событиям;
- follow-up по semantic результатам;
- формирования narrative и гипотез;
- диалогового ответа по предыдущему отчёту.

Это production-only поведение. Testing runtime не импортирует и не вызывает
данный adapter.

### 9.2. Semantic index

Production semantic-компонент:

```text
workspace/skills/ior-analyzer/utils/bge_search_engine.py
```

Он поддерживает:

- использование заранее рассчитанных embeddings;
- малый индекс для текущей session selection;
- поиск по описаниям выбранных ИОР;
- проверку соответствия найденных ID исходной выборке;
- тяжёлый production retrieval stack для закрытого контура.

Follow-up не должен искать по чужим сессиям или по глобальной выборке, когда
пользователь явно спрашивает о предыдущем отчёте.

## 10. Production sessions

### 10.1. In-memory extract

```text
workspace/skills/ior-analyzer/utils/session_extract_manager.py
```

Хранит для `session_id` активный DataFrame и связанные metadata. На одну
сессию приходится одна активная выборка; новый анализ заменяет предыдущую.

### 10.2. Session files

```text
workspace/skills/ior-analyzer/utils/session_file_store.py
```

Отвечает за:

- безопасное имя session directory;
- metadata сессии;
- сохранение результатов;
- ограничение числа/возраста файлов;
- архивирование и cleanup.

### 10.3. Изоляция

Ключ берётся из request context nanobot. Поэтому две вкладки или две беседы
Audit-Workstation не разделяют один `webui_session`.

## 11. Production output и delivery contract

### 11.1. Файлы

Production экспортирует результаты в:

```text
workspace/data_store/generated_files/
```

Для непустой выборки создаются:

- CSV в UTF-8;
- XLSX через `openpyxl`, с дополнительными fallback-ветками записи.

### 11.2. Артефакты

```text
workspace/skills/ior-analyzer/utils/artifact_manager.py
```

Модуль умеет:

- разрешать путь к артефакту;
- определять MIME-type;
- формировать metadata файла/графика;
- при допустимом размере кодировать файл для транспорта;
- добавлять артефакты в результат.

### 11.3. Lossless delivery

`SKILL.md` содержит маркер:

```text
FINAL_DELIVERY_MODE: IOR_REPORT_VERBATIM_V1
```

Успешный отчёт является готовым пользовательским ответом. Agent не должен:

- пересказывать его;
- сокращать таблицы;
- удалять гипотезы;
- выполнять второй LLM summary-pass;
- переставлять разделы;
- добавлять собственные выводы.

Если канал имеет жёсткий лимит, исходный отчёт делится на последовательные
части без потери строк.

## 12. Production graceful fallback

Если получение production-данных завершилось ошибкой, исключение должно дойти
до Tool boundary: недоступность БД нельзя маскировать как корректный результат
с нулём строк.

Если данные получены, но генерация narrative не удалась, функция
`build_graceful_fallback_report()` строит детерминированный отчёт из DataFrame:

- количество строк/событий;
- суммы;
- статусы;
- top-наблюдения;
- ссылка/карточка XLSX, если файл был создан;
- явное предупреждение об ошибке narrative.

Это не переключение в testing, а безопасное завершение production-анализа на
уже полученных production-данных.

## 14. Testing runtime

Testing полностью расположен рядом с production и не копирует production
pipeline:

```text
workspace/skills/ior-analyzer/testing/
├── __init__.py
├── data_generator.py
├── runner.py
├── unit_checks.py
└── README.md
```

### 14.1. Генератор

```text
testing/data_generator.py
```

Параметры:

- фиксированный seed: `20260921`;
- размер: ровно `1000` записей;
- генератор: отдельный `random.Random(seed)`;
- уникальный ID: `EVE-TEST-0001` … `EVE-TEST-1000`;
- DRP: только `DRP-TEST-*`;
- период дат: синтетический диапазон 2024–2026;
- генерация по требованию при отсутствии файла;
- `--force` для явной регенерации.

Результат хранится здесь:

```text
workspace/data_store/cache/testing/ior/ior.json
```

При одинаковом seed порядок и содержимое набора идентичны.

### 14.2. Поля synthetic record

| Поле | Смысл |
|---|---|
| `eve_id` | Уникальный тестовый EVE |
| `drp` | Синтетический DRP |
| `date` | Дата события |
| `event_type` | Тема события |
| `category` | Категория риска |
| `description` | Короткое обезличенное описание |
| `status` | Синтетический статус |
| `financial_loss` | Сумма тестовых потерь |
| `reimbursement` | Тестовое возмещение |
| `business_line` | Обобщённая бизнес-линия |
| `product` | Обобщённый продукт |
| `channel` | Канал |
| `cause` | Причина |
| `consequences` | Обобщённые последствия |

Тематические кластеры покрывают комиссии, двойные списания, технические сбои,
мошенничество, человеческий фактор, недоступность, расчёты, переводы, данные и
кредитный процесс. Эти формулировки полностью синтетические.

### 14.3. Testing flow

```text
prompt
  ↓
load_records() / ensure_testing_data()
  ↓
если follow-up — ограничение предыдущими selected_ids этой сессии
  ↓
детерминированные EVE/DRP/date filters
  ↓
numeric intent?
  ├── да → Python count/sum/average/reimbursement
  └── нет → lexical shortlist ≤ 60
               ↓
           shared LLM JSON selection
               ↓
           валидация returned eve_id
  ↓
сохранение session state
  ↓
Markdown report + evidence ≤ 20 строк
```

### 14.4. Детерминированные операции

Без LLM выполняются:

- точный поиск `EVE-TEST-*`;
- точный фильтр `DRP-TEST-*`;
- фильтр по одной дате или диапазону;
- количество записей;
- сумма `financial_loss`;
- средняя величина потерь;
- сумма `reimbursement`.

Это обеспечивает повторяемые числовые ответы.

### 14.5. Semantic search

Для смыслового запроса:

1. Из prompt извлекаются значимые слова длиной от четырёх символов.
2. Python ранжирует записи по числу lexical совпадений.
3. В LLM передаётся не более 60 коротких кандидатов.
4. LLM получает только ID, дату, описание и категорию.
5. Ожидается JSON с существующими `eve_id`.
6. Любой ID вне candidate set отбрасывается.

Все вызовы идут через:

```text
lib.services.llm_client.call_llm_json
```

Клиент использует provider/model/apiBase/apiKey текущего nanobot. Testing не
содержит собственных ключей и не обращается к production `local_qwen.py`.

### 14.6. Testing sessions

Состояние хранится отдельно от production:

```text
workspace/data_store/cache/testing/ior/sessions/<safe-session>.json
```

Формат:

```json
{
  "query": "обезличенный запрос",
  "selected_ids": ["EVE-TEST-0001"]
}
```

Follow-up-маркеры вроде «среди них» или «в этой выборке» ограничивают новый
расчёт только ID из предыдущего результата текущей session.

## 15. Что testing намеренно не делает

Testing D6 не:

- подключается к Greenplum/Spark/Hive;
- использует production connection pool;
- читает production cache;
- импортирует production BGE/FAISS pipeline;
- требует CUDA/GPU;
- вызывает локальный vLLM;
- обращается к corporate LLM adapter;
- создаёт реальные EVE/DRP;
- автоматически подменяет упавший production runtime.

## 16. Тесты

Testing unit checks находятся в:

```text
workspace/skills/ior-analyzer/testing/unit_checks.py
```

Они подключены к корневому pytest через:

```text
tests/test_external_testing_runtimes.py
tests/test_external_testing_tool_adapters.py
tests/test_skill_runtime_mode.py
```

Проверяются:

- ровно 1000 записей;
- уникальность EVE ID;
- одинаковый seed → одинаковые данные;
- EVE/DRP/date filters;
- count и sum;
- session isolation;
- testing route native Tool adapter;
- production по умолчанию;
- ошибка на неизвестном runtime flag.

LLM в unit-тестах мокируется, реальные сетевые вызовы не выполняются.

## 17. Запуск

### Production

Дополнительная переменная не нужна:

```powershell
Remove-Item Env:NANOBOT_SKILLS_RUNTIME -ErrorAction SilentlyContinue
```

### Testing

Перед запуском nanobot/bridge child process:

```powershell
$env:NANOBOT_SKILLS_RUNTIME="testing"
```

### Регенерация synthetic data

Из корня `audit_nanobot`:

```powershell
python workspace/skills/ior-analyzer/testing/data_generator.py --force
```

Если `python` не доступен в `PATH`, нужно использовать Python того venv,
которым запускается nanobot.

## 18. Безопасные примеры проверки

Числовой запрос:

```text
Сколько ИОР по DRP-TEST-001 и какова сумма тестовых потерь и возмещений?
```

Точный запрос:

```text
Покажи сведения по EVE-TEST-0001.
```

Semantic запрос:

```text
Найди синтетические случаи двойного списания или ошибочной комиссии.
```

Follow-up:

```text
А сколько среди них событий без финансовых потерь?
```

Все примеры работают только с synthetic ID и не должны заменяться реальными
production-идентификаторами в публичной документации.

## 19. Диагностика

### Не выбран testing

Проверить значение:

```powershell
$env:NANOBOT_SKILLS_RUNTIME
```

Переменная должна быть задана в процессе, который непосредственно запускает
nanobot, либо в его родительском bridge-процессе.

### Сессии смешиваются

Проверить лог request session key. Frontend-вызов не должен использовать
`webui_session`; ожидается `postgres:<conversation UUID>`.

### Dataset не создаётся

Проверить права записи для:

```text
workspace/data_store/cache/testing/ior/
```

и запустить generator с `--force`.

### Semantic ответ пуст

Проверить конфигурацию общего provider nanobot и ответ
`lib.services.llm_client`. Testing runner не переключается на локальный LLM.

### Production обращается к testing data

Это считается дефектом. При unset/`production` adapter обязан вызывать только
`run_ior_report`; testing package не должен импортироваться.

## 20. Инварианты сопровождения

1. Production всегда остаётся default.
2. Testing включается только точным значением `testing`.
3. Production и testing данные не смешиваются.
4. Testing ID всегда имеют `TEST`-префикс.
5. Числовые показатели testing считаются Python-кодом.
6. LLM ID всегда валидируются относительно candidate set.
7. Весь внешний LLM-трафик идёт через shared nanobot client.
8. `workspace/utils/db.py` не изменяется ради D6 testing.
9. Frontend session key имеет приоритет над `webui_session`.
10. Production report передаётся пользователю losslessly.
