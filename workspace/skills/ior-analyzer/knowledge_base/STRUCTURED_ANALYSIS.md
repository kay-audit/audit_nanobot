# Структурированный анализ ИОР

Это отдельный режим существующего skill, не natural-language preset.
Canonical envelope с первым маркером `Анализ ИОР` и прежний полный JSON в
`--prompt` проверяются до сессий, Greenplum, Qwen и preset detector. Ошибка
распознанного structured-контракта не переводит запрос в обычный режим. Явный
`--preset` или внешние `filters` вместе со structured prompt возвращают ошибку
конфликта.

Предпочтительный формат для пользовательского UI:

```text
Анализ ИОР

Денежный показатель:
Прямые потери

Оргструктура:
Все

Период:
01.01.2026 — 30.06.2026

Сформировать Excel:
Да
```

Labels обязательны, уникальны и пишутся точно как в примере. Порядок блоков не
значим. Значение периода имеет формат `DD.MM.YYYY — DD.MM.YYYY`, обе даты
обязательны и включены. Для Excel допустимы только `Да` и `Нет`.

Прежний JSON-контракт полностью поддерживается:

```bash
bash ior_analyze.sh --prompt '{"action":"Анализ","money_filter":"Прямые потери","org_filter":null,"date_range":"2026-01-01:2026-06-30","export_excel":false}'
```

Для детального Excel измените `export_excel` на JSON boolean `true`.
`action` и `money_filter` допускают нормализацию регистра и пробелов.
`money_filter` и `date_range` обязательны. Период — строго
`YYYY-MM-DD:YYYY-MM-DD`, конечный день включён. Непустой `org_filter`
пока не поддерживается; строки вместо boolean отклоняются.
Неизвестные и повторяющиеся JSON-поля отклоняются, чтобы не игнорировать фильтры.
JSON-подобный prompt зарезервирован для этого контракта, включая повреждённые
объекты и массивы. Обычный естественный текст не включает structured analysis.
Точный canonical-маркер также зарезервирован: повреждённый envelope после
`Анализ ИОР` возвращает validation error и не проваливается в legacy routing.

## Поток данных

`AnalysisRequest` → registry денежного фильтра → SQL strategy → detail →
incident → approved detail/incident → month + incident → statistics →
anomaly events → evidence pack → локальный Qwen → три раздела → optional XLSX.

- `models.py`, `parser.py`: typed-контракт и validation.
- `registry.py`, `direct_loss.py`: стратегия и SQL через `store.tables`.
- `statistics.py`: полные показатели, approved TOP-10, непрерывный месячный ряд,
  средняя потеря на ИОР, полнота граничных месяцев и помесячные концентрации.
- `anomalies.py`: статистические выбросы, изменения месяц к месяцу, общие и помесячные
  концентрации, смена лидера и связь сигналов с ИОР.
- `hypotheses.py`: разнообразный evidence, Markdown Qwen, один retry и fallback.
- `report.py`, `export.py`, `runner.py`: итоговый формат, export policy, orchestration.

SQL соединяет `ior.incdnt_id = fi.incdnt_id`, отбирает только
`fin_impact_type_name = 'Прямая потеря'` и даты
`fin_impact_creation_dttm >= start AND fin_impact_creation_dttm < end + 1 day`.
Ограничения числа строк и предикатов по lifecycle-датам main нет.
Нулевые и NULL-последствия остаются. Технические номера счетов/документов не выбираются.

Detail дедуплицируется по `(incdnt_id, fin_impact_sid)`; при конфликте сумм
сохраняется первая строка, в отчёте отражается замечание о качестве данных.
Без SID строки сохраняются: невозможно доказать их дублирование.
Canonical key ИОР — `incdnt_id`; EVE используется для отображения.
NULL даёт нулевой вклад в сумму, но классификация отличает `null/unknown`
от реального нуля. Смесь нуля и NULL считается zero, наличие положительной
суммы — positive. Месячная классификация считается заново по деталям месяца.

Полная выборка всех статусов используется для общей численности, общей суммы,
фактических статусов и Excel. Вся остальная аналитика и evidence используют
бизнес-группу approved из `preset_analysis/common.py`.
Один ИОР может входить в несколько месяцев, но только один раз в каждом.
Доли positive/zero имеют знаменатель всех ИОР месяца, включая unknown.

## Правила сигналов и гипотез

Денежные выбросы: положительные суммы ИОР выше `Q3 + 1.5 * IQR`.
Месячные выбросы: суммы, числа ИОР и доли вне `Q1 − 1.5 * IQR .. Q3 + 1.5 * IQR`.
IQR применяется минимум на четырёх достаточно полных месяцах при ненулевом
размахе. Начальный месяц достаточно полон, если начало периода не позже
третьего календарного дня; конечный — если до последнего дня отсутствует не
больше двух дней. Остальные граничные месяцы получают `is_partial_month=true`:
они остаются в таблице и evidence, отмечаются `*`, но не участвуют в месячном
IQR и MoM. Пара месяцев также не сравнивается, если любой из них partial.
Пустые месяцы показаны в динамике, но их доли не входят в IQR и сравнение долей.
Для малых/вырожденных выборок выводятся крупнейшие наблюдения без заявления
о статистической аномалии. Изменение после нуля описывается без процента роста.
Общие концентрации от 50% суммы либо числа ИОР по ТБ, ЦПР и процессу,
изменения долей positive/zero от 25 п.п. — описательные screening rules.
Для каждого месяца и значения ТБ, пары `risk_profile_id + risk_profile_name`
и процесса рассчитываются число ИОР, сумма, доля месячной суммы и доля числа
ИОР. Изменение категории считается существенным при абсолютном сдвиге от
20 п.п. и доле хотя бы в одном из месяцев от 30%. Детектор различает рост,
новую концентрацию из нулевой/отсутствующей категории, снижение и смену лидера
с силой перехода от 20 п.п. Нулевая месячная сумма даёт долю 0 без inf/NaN.
Сигналы между partial/full месяцами не создаются. Дополнительно выявляются:
расхождение частоты и денежной тяжести при изменениях от 20% (сильное изменение
средней потери — от 30%); диспропорция долей суммы и количества от 20 п.п. при
значимости одной из долей от 30%; доминирование категории от 50% не менее трёх
полных месяцев подряд; монотонный тренд доли не менее трёх полных месяцев с
общим изменением от 20 п.п. Все пороги детерминированы в Python; наблюдения не
доказывают причину. Пользовательский список обычно содержит до восьми событий.
Сначала действует лимит двух событий на месяц, затем свободные места заполняются
следующими сильными сигналами, если альтернатив недостаточно.

Полная статистика рассчитана до отбора текстовых примеров. Event-driven выборка
смешивает типы, измерения и месяцы, берёт крупнейшие и характерные случаи и
ограничивает вклад одного события шестью ИОР. Итог — до 60 уникальных ИОР.
Они обрабатываются батчами по 10 через обычный `ask_local_qwen()`: максимум шесть
батчей и не более трёх одновременных запросов, как в старом рабочем pipeline.
Каждый батч возвращает краткую аналитическую выжимку; ошибка одного батча
журналируется и не останавливает остальные или финальную генерацию.

Финальный prompt содержит до 12 рассчитанных наблюдений, выжимки успешных
батчей и несколько ключевых прямых примеров. Целевой размер — до 24 000 символов,
жёсткий предохранительный предел — 40 000. Избыток низкоприоритетного evidence
сокращается и не прерывает вызов Qwen. Ограничения относятся только к контексту
модели и не меняют расчёты по полной выборке.

Structured analysis вызывает обычный `ask_local_qwen()` тем же способом, что и
рабочий `ior_hypothesis`, и получает готовый Markdown раздела 3. От модели не
требуются JSON, `signal_ids` или `evidence_ids`. Валидатор проверяет только один
заголовок раздела 3, последовательные гипотезы 1–3, обязательные части, минимум
два нумерованных шага и отсутствие EVE, которых не было в переданных примерах.
Связь EVE с внутренними signal-ID не проверяется. После первой ошибки исходный
компактный prompt собирается заново с точной причиной; предыдущий ответ в history
не добавляется. Если исправленный Markdown также неполон, содержит неизвестный
EVE либо сервис недоступен, fallback строит три проверки из реальных событий.
В логах есть размер prompt, число примеров, размер ответа, полнота, причина
валидации и источник `qwen` или `fallback`; полные описания не пишутся.

## Вывод и файлы

При наличии данных ровно три заголовка: `1. Общая статистика`,
`2. Временной анализ и аномалии`, `3. Гипотезы`.
Пользовательская часть отчёта использует русские бизнес-термины. Месячная
таблица содержит месяц, количество ИОР, сумму прямых потерь и среднюю потерю
на ИОР. Методика
расчёта порогов остаётся внутренней; перед перечнем сигналов выводится одно
общее пояснение, что это основания для проверки, а не подтверждённые причины.
При пустом SQL-результате — короткое сообщение, без Qwen и Excel.
При отсутствии approved — общая статистика, пояснения в разделах 2/3,
без Qwen, но полный Excel при `true`.

Файлы создаются только при `export_excel=true`: XLSX в
`workspace/data_store/generated_files`, определённом относительно установки skill.
В нём все дедуплицированные последствия всех статусов, технические названия
аналитически полезных колонок и `amount_is_null`. Большая выгрузка разделяется
по листам по вместимости Excel, без потери строк. CSV и Excel-card отсутствуют.
Сессионное извлечение/BGE-индекс этим режимом не создаются.

## Offline tests

Из корня репозитория, в Python-окружении проекта:

```bash
python -m unittest discover -s workspace/skills/ior-analyzer/scripts -p test_analysis_mode.py
python -m unittest discover -s workspace/skills/ior-analyzer/scripts -p test_preset_analysis.py
python -m unittest discover -s workspace/skills/ior-analyzer/scripts -p test_vozmeshenie_aggregation.py
python -m compileall -q workspace/skills/ior-analyzer/scripts
```

Новые тесты используют synthetic DataFrame, SQLite для проверки SQL и mocks,
не требуют работающих Greenplum или Qwen. Старые пресеты и их SQL/export policy
не изменены. Для нового денежного фильтра добавьте strategy в `MONEY_FILTERS`
и соответствующие предметные метрики/подписи: существующие presets не переписываются.

Проверка реализации 2026-09-10: 69 новых unittest, 46 существующих
`test_preset_analysis` и 6 `test_vozmeshenie_aggregation` прошли.
Отдельно прошли обе проверки `utils/resolve/test_resolve.py` и четыре из пяти
выбранных offline-функций `test_ior.py` (SQL пресетов, маршрутизация кодов,
порядок колонок Excel, пятнадцать аудиторских запросов).
`test_complex_adhoc_query_builder` ожидает `incdnt_sum >=`, хотя существующий
builder использует `SUM(COALESCE(fin_impact_rub_amt, 0))` в financial scope.
Та же ошибка воспроизведена с удалённым в памяти новым dispatch — это
существующее несоответствие теста. Старый SQL и тест не изменялись.
Syntax/import и skill frontmatter validation прошли. CLI с обоими значениями
export проверен на synthetic данных. Live GP/Qwen не запускались; pytest-наборы
корня не запускались из-за отсутствия pytest в доступном Python.
