# Архитектура предметной аналитики ИОР

## Единый runtime-контракт

Каждый активный пресет подготавливает `AnalysisBundle` с четырьмя независимыми представлениями:

1. `raw_df` — исходная физическая выгрузка для диагностики качества данных.
2. `incident_all_df` — одна запись на `incdnt_sid`; используется для распределения статусов.
3. `analysis_detail_df` — уникальные дочерние сущности только утверждённых ИОР; используется для предметных сумм и классификаторов detail-таблицы.
4. `analysis_incident_df` — одна запись на утверждённый `incdnt_sid`; используется для процессов, оргструктуры, EVE-примеров, текстов, Qwen и гипотез.

Для обычных пресетов аналитическая выборка содержит только статусы `Утверждён`, `Утвержден`, `Утверждение`. При нуле таких ИОР выборка остаётся пустой: возврата к полной выгрузке нет, аналитические разделы и гипотезы не формируются.

`deleted_ior` является исключением: это журнал действий удаления, искусственная группировка статусов для него не строится.

## Ответственность модулей

- `scripts/preset_analysis/common.py` — общий typed-контракт, статусы и технические helpers.
- `scripts/preset_analysis/registry.py` — единственный dispatch активных пресетов.
- остальные файлы каталога — предметная гранулярность, метрики, структура разделов и prompt rules конкретного пресета.
- `scripts/ior_hypothesis.py` — orchestration локального Qwen, batching текстов, validation/postprocessing и графики.

Разделы 1–3 формируются детерминированно. Qwen получает уже отфильтрованный analytical dataset и используется для текстовых наблюдений и проверочных гипотез.

Для detail-пресетов рабочая гранулярность и Excel дедуплицируются по `(incdnt_sid, child_sid)`: `recovery_sid`, `fin_impact_sid` или `nonfin_impact_sid`. Разные дочерние SID одного EVE сохраняются. Конфликт сумм у одной пары считается data-quality issue; используется первая строка и пишется warning.

Chart и Excel-card управляются явной политикой пресета. Financial не может выбрать recovery, nonfinancial/deleted не показывают денежные итоги. Qwen получает контекст пользовательских фильтров и не должен трактовать заранее выбранную категорию как обнаруженную концентрацию.

## QuerySpec

Компилятор сохраняет `analysis_df_id` после pre-aggregated joins, всех incident-level фильтров и безопасных derive, но до финальной агрегации. При post-aggregate/HAVING-фильтре candidate дополнительно ограничивается ключами групп, переживших фильтр. Если восстановить incident-level scope невозможно, используется только фактический aggregate с явным предупреждением о гранулярности — более широкая population молча не анализируется. Финальный `df_id` и Excel сохраняют исходный смысл QuerySpec; fan-out protection, lineage, funnel и methodology sheet не изменяются.

## Неиспользуемый пресет

`credit_no_way_collect_debt` намеренно не включён в registry и automatic routing и продолжает использовать прежний compatibility path только при явном вызове.
