# Восстановление бизнес-контрактов D6 IOR

Исходное состояние: `feature/d6_ior`, `a4728385ee1728eee78826afd7eac8432752c2cd`.
Изменения предназначены только для этой исходной ветки; публикация и интеграция
в `finalize_nanobot` в эту задачу не входят.

## Подтверждённые наборы полей

Основание — перечисления бизнес-полей в семи спецификациях
`knowledge_base/scripts/`, mapping, `ANALYSIS_ARCHITECTURE.md`, а также
машиночитаемый снимок production-схемы `utils/schema/kb_schema.yaml`.
Это подтверждение по репозиторию, **не по реальным закрытым данным**.
Локальный `~/.cache/nanobot/duckdb/cache.duckdb` существует, но не содержит таблиц.
Все исполняемые проверки выполнялись на изолированных DuckDB fixtures.

| Preset | Заявлено | Подтверждено схемой / XLSX fixtures | Состав | Гранулярность |
|---|---:|---:|---|---|
| `ior_hypothesis` | 67 | 64 | Все 64 main | Один уникальный ИОР |
| `financial_consequences_ior` | 67 | 64 | 47 атрибутов main + 17 fin impact | `(incdnt_sid, fin_impact_sid)` |
| `vozmeshenie_ior` | 61 | 58 | 47 атрибутов main + 11 recovery | `(incdnt_sid, recovery_sid)` |
| `deleted_ior` | 83 | 71 | Все 64 main + 7 полей действия | Действие удаления; без истории остаётся main |
| `ior_nonfinancial_consequences` | 53 | 50 | 47 атрибутов main + 3 nonfinancial | `(incdnt_sid, nonfin_impact_sid)` |
| `report_period_specific_ior` | 95 | 92 | Все 64 main + 17 fin impact + 11 recovery | Raw-комбинации fin impact × recovery |

Точный список каждого набора — `report_field_contracts.json`: technical_name,
source, source_column, excel_label, order, required,
present_repository_schema, live_cache_schema. Файл служит фиксированным golden
контрактом regression-тестов, а не вычисляется заново при их запуске.

Main состоит из 47 атрибутов и 17 агрегатов: 16 показателей потерь/прибыли и
`recovery_rub_amt_aggr`. Специализированные отчёты financial/recovery/nonfinancial
используют атрибуты без этих агрегатов: деньги берутся из соответствующего detail.
Удаления, общий отчёт и досье сохраняют полный main. `incdnt_id` detail не
дублируется в XLSX; статус журнала назван `incdnt_status_name_at_action`, его код —
`incdnt_status_code_at_action`, чтобы не сталкиваться с текущим статусом main.

## Противоречия спецификаций

- Mapping перечисляет 64 уникальных main-поля при заявленных 67. Перечисление
  атрибутов содержит 47 полей, хотя исторически объявлено 50; в нумерации
  специализированных отчётов имеются пропуски. Недостающие три поля не выдуманы.
- Отсюда 47+17=64 для финансов, 47+11=58 для возмещений, 47+3=50 для
  нефинансовых последствий, 64+17+11=92 для досье. Заголовочные числа
  67/61/53/95 не соответствуют перечислениям.
- Для удалений перечислены main и семь бизнес-полей действия: 64+7=71,
  а не 83. Схема журнала имеет ещё FK `incdnt_id` и `start_dt`;
  FK используется для связи, `start_dt` — техническая валидность записи,
  не заявленное бизнес-поле действия. Они не добавляются ради числа 83.
- В описании финансовой таблицы встречаются одновременно 17 и 18 полей:
  всего их 18 с FK, самостоятельных detail-полей 17. `fin_impact_type_name`
  существует в снимке; `fin_impact_subkind_name` отсутствует и не используется.
- Локальный DDL V006 и снимок production-схемы различаются: main DDL не
  содержит `clntpth_lvl_4_name`, добавляет `incdnt_status_code` и `created_at`;
  status DDL не содержит `start_dt`. Миграция для этих проверок не запускалась.
- В старых текстах разные дефолтные пресеты, технологии выполнения и пороги
  гипотез. Применён текущий контракт: общий отчёт `ior_hypothesis`,
  backend через существующий store/cache, гипотезы от 50 уникальных ИОР,
  досье без гипотез. Эти инфраструктурные механизмы не переписывались.

При реальном запуске нулевой `SELECT * ... WHERE 1=0` используется **только для
метаданных main** через уже выбранный store. Запрос данных всегда содержит
явную проекцию. Порядок известных полей фиксирован, реально добавленные атрибуты
следуют по алфавиту. Отсутствующие дополнительные поля диагностируются, основные
ключи/статус/дата обязательны. Данные отсутствующих полей не подменяются NULL.
При отличающейся реальной схеме число колонок может отличаться от таблицы выше.

## Что восстановлено относительно старой реализации

Сравнены `ior_reports.py` из `2b01856aca9e97410420a1a8e2663a061ad41a7f`,
проблемного `89da442061d286ad76585d5acd1728487444bc11` и исходного HEAD задачи.
Старые `ior.*` действительно сохраняли полный main на SQL-этапе. Замена на
24 поля убрала до 40 атрибутов подтверждённой витрины до экспорта: уровни
оргструктуры и функционального блока, договоры/заявки, флаги рисков, даты,
клиентский путь и агрегаты. В динамическом финансовом запросе также терялся
`fin_impact_id`. Старые Excel whitelist уже не содержали двух level-4 полей,
поэтому одного восстановления SQL было бы недостаточно.

Восстановлены явные полные проекции и все три nonfinancial detail-поля,
сохранён `fin_impact_type_name`. Финансовые и recovery отчёты остаются INNER JOIN;
удаления и оба соединения досье — LEFT JOIN. Журнал сохраняет известные
действия delete/toDelete/approveDelete/approveDeletion/sendForDeletion/
confirmDeletion и действие с именем «Удалить». `rejectDeletion` сам по себе
не считается удалением. Дата отбора удалений — дата ввода ИОР, не дата действия.
Исторический скрытый `LIMIT 100000` общего динамического запроса не возвращён.

## Маршрутизация и XLSX

Tool явно передаёт `trusted_preset=False`: LLM-подсказка не является выбором
пользователя. CLI по-прежнему использует доверенный технический preset.
Общие запросы, в том числе «общая сумма потерь», идут в main; специализированный
смысл выбирает detail. EVE без специализации — досье, со специализацией — фильтр
соответствующего отчёта. Противоречивые специализированные намерения требуют
уточнения. Денежные пороги, loss-tab guard, structured analysis и явный follow-up
сохранены; legacy ПАО автоматически не выбирается.

Пустая выборка не вызывает запросов с ослаблением фильтров. Нет подмены данных
результатом диагностики. Исправлен вторичный периодный фильтр DataFrame:
приоритет отдаётся именно колонке распознанного периода, а не первому похожему
столбцу, который мог быть пустым.

Excel сохраняет SQL-порядок и русские заголовки. Не применяется повторный короткий
whitelist. Большие ID и номера сохраняются как текст, nullable `fin_impact_id`
передаётся из SQL строкой до преобразования в pandas, денежные NULL не становятся
нулём. Одноимённые даты и документы разных detail получили разные русские
подписи. Main-дубликаты не складывают уже агрегированные деньги. Detail
дедуплицируется по инциденту и SID; raw-досье сохраняет шесть комбинаций 3×2,
аналитика независимо считает три финансовых последствия и два возмещения.
Встроенная кредитная проекция и агрегация оставлены прежними.

Используется существующий атомарный writer с fsync и повторным открытием XLSX;
отключение вторичного форматирования не отключает проверку файла. Текст,
похожий на формулу, остаётся текстом в обоих engines. Доставка MessageTool
и request-local artifact scope не изменены.

## Проверки и ограничения

`test_restored_contracts.py` создаёт реальные in-memory DuckDB таблицы по снимку
схемы, проверяет все примеры routing с неправильными LLM-подсказками, полные
составы и порядок полей всех шести XLSX через openpyxl, 19-значные номера,
ID больше 2^53, NULL, даты, суммы, досье без детей, два удаления и отсутствие
истории, март `[2025-03-01, 2025-04-01)` и Среднерусский банк именно на уровне 3.
Проверяется вариант main-схемы без клиентского пути с добавленной датой создания,
нерасширение пустой выборки и fallback записи без xlsxwriter.

Первый baseline: 273 passed, 67 subtests passed, 2 failures из-за отсутствия
инициализации SETTINGS в standalone pytest. Для сравнимого полного запуска
конфигурация явно инициализируется `config._initialize_settings('test')`
перед `pytest.main(...)`; сервисы не запускаются. Итог: **334 passed,
2 skipped, 67 subtests passed**, 147.86 секунды. Две пропущенные проверки —
регистрация таблиц D6 в локальном профиле и их передача sync-service;
причина: `Local project profile has no IOR table registration`.
Это ограничение окружения, а не подтверждение production-регистрации.
Все шесть проверок полного SQL → XLSX pipeline прошли. К исходным успешным
проверкам добавлены 57 новых business-regression случаев; тесты расширения
источника заменены проверками запрета расширения, что даёт ещё четыре случая.

Команда воспроизведения (интерпретатор с pytest, DuckDB, pandas, openpyxl):

Полный проект не пересобирался, реальные GP/PG/OSIRIS и LLM не вызывались.
