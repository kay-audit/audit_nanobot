# IOR Analyzer

`FINAL_DELIVERY_MODE: IOR_REPORT_VERBATIM_V1`

Анализирует локальную Базу знаний ИОР, формирует детерминированные показатели,
гипотезы и выгрузки Excel/CSV. Данные ИОР конфиденциальны: обрабатывай тексты
только локальными компонентами и Qwen vLLM; не отправляй их во внешние API.

## Контракт вызова и ответа

- Передавай в параметр `prompt` **полный исходный prompt пользователя** без
  пересказа, сокращения, исправления формулировок или выделения одной части.
- Не заменяй prompt автоматически составленным описанием намерения. Параметр
  `preset` дополняет prompt, но не подменяет его.
- Успешный результат скилла является готовым ответом. Выведи **полный ответ
  LLM/скилла от первой до последней строки**, сохранив порядок, Markdown,
  таблицы, числа, гипотезы, пути и ссылки на файлы.
- Не делай после скилла summary-pass и не добавляй собственное вступление или
  заключение. Преобразование допустимо только по явному запросу пользователя.

## CRITICAL: LOSSLESS FINAL OUTPUT CONTRACT

`ior_analyzer` — authoritative formatter и authoritative final-answer producer.
Сформированный им отчёт уже является окончательно отформатированным ответом
пользователю и source of truth для финального текста.

After a successful `ior_analyzer` call, switch from ANALYSIS mode to DELIVERY
mode. В DELIVERY mode роль caller/AgentLoop/Nanobot — только передача результата:

`FINAL_RESPONSE = TOOL_RESULT`

MUST NOT запускать повторный analytical pass, synthesis pass, reasoning,
extraction, ranking, rewriting или другой LLM post-processing. MUST NOT
пересказывать отчёт, формировать новый ответ «по мотивам», выбирать главное,
добавлять собственное вступление, заключение или рекомендации.

### Обязательная lossless-передача

Пользователю MUST быть передан полный user-facing report verbatim/losslessly —
от первой строки до последней, в исходном порядке. Сохраняй заголовки,
подзаголовки, нумерацию, списки, таблицы, Markdown, смысловые переносы, все
значения, идентификаторы, периоды, количественные показатели, оценки, evidence,
ограничения, предупреждения, пути и ссылки.

MUST NOT сокращать, summarize, compress, paraphrase, rewrite, simplify,
«улучшать читаемость» удалением деталей, переставлять блоки, менять выводы или
формулировки, выбирать только важные части, удалять строки либо секции. Нельзя
отбрасывать материал как длинный, повторяющийся, второстепенный или
маловероятный. Экономия токенов NEVER является основанием сокращать IOR report:
полнота имеет приоритет над краткостью и общими concise/style-инструкциями.

### Гипотезы атомарны

Каждая гипотеза — самостоятельная обязательная часть результата. Если skill
сформировал N гипотез, пользователь MUST получить все N гипотез в том же
порядке. Количество гипотез в tool result и финальном ответе MUST совпадать.
Полное описание, причины, обоснования, evidence, ограничения и formatting
каждой гипотезы обязательны.

MUST NOT:

- показывать только первые или «основные» 3/5/10 гипотез;
- выбирать наиболее вероятные гипотезы;
- объединять похожие гипотезы;
- сокращать гипотезу до названия, одной строки или summary;
- заменять подробный список одной общей гипотезой.

### BAD / GOOD

BAD — tool вернул три подробные гипотезы по 8–12 строк, а Nanobot ответил:

> Выявлены три основные гипотезы: ошибки процесса, контрольные недостатки и
> человеческий фактор.

Это КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО.

BAD — вывести только:

> Основные гипотезы: 1. ... 2. ... 3. ...

если tool result содержал подробное описание каждой гипотезы.

GOOD — передать полный исходный текст всех трёх гипотез со всеми подробностями,
обоснованиями, evidence, порядком и Markdown без смысловых изменений.

### Transport envelope, длинный вывод и ошибки

Если результат обёрнут в технический объект с полями `status`, `answer`,
`result` или `message`, техническую envelope печатать не нужно. Но поле с
готовым пользовательским отчётом MUST быть передано полностью и без изменений.

Если реальный лимит канала не позволяет отправить отчёт одним сообщением,
MUST NOT сокращать его. Разбей исходный текст на последовательные части
`Часть 1/N`, `Часть 2/N`, ...; сохрани порядок и не пропусти ни одной строки или
секции. Не резюмируй предыдущие части. Если лимита нет — передай одним сообщением.

Этот контракт относится к SUCCESS result. При ошибке допустимо краткое понятное
сообщение без лишнего traceback. Явное преобразование отчёта допустимо только в
последующем пользовательском запросе, который прямо просит summary, сокращение
или другую трансформацию; первоначальный успешный результат всегда передаётся
losslessly.

## Режимы

| Режим | Когда использовать |
|:------|:-------------------|
| `preset` | Запрос соответствует одной из стандартных выгрузок |
| `ad-hoc` | Нестандартные фильтры, периоды, оргструктура, коды или суммы |
| `follow-up` | Вопрос относится к сохранённой выгрузке текущей сессии |
| `structured analysis` | Prompt — canonical envelope `Анализ ИОР` или JSON с `"action":"Анализ"`; передавай без `preset` |

Структурированный анализ — отдельный pipeline в `scripts/analysis_mode/`.
Предпочтительный вход для пользовательского UI — canonical human-readable
envelope с первым маркером `Анализ ИОР`; прежний строгий JSON остаётся
backward-compatible входом.
Не преобразовывай обычный текст о прямых потерях в JSON: он сохраняет старую
маршрутизацию `financial_consequences_ior`. Контракт, ограничения и тестовые
команды: [STRUCTURED_ANALYSIS.md](knowledge_base/STRUCTURED_ANALYSIS.md).
Structured-режим формирует ровно три раздела и сохраняет только XLSX при явном
`export_excel=true`; при `false` файлы выгрузки не создаются.

Новый запрос с `EVE-<номер>` маршрутизируй в досье конкретного ИОР. Если
пользователь явно ссылается на прошлую выгрузку, отвечай по сессионным данным:
для конкретного EVE используй точное совпадение, для смыслового вопроса — малый
FAISS-индекс текущей выгрузки.

`report_period_specific_ior` разрешён **только** при наличии конкретного
`EVE-<номер>`. Коды `DRP-*`, `SBR-*`, процессы, периоды, оргструктура и суммы —
это ad-hoc фильтры: используй `ior_hypothesis` либо не передавай `preset`, чтобы
его определил сам анализатор.

## Семантический follow-up

Используй IOR-cache:
`workspace/data_store/cache/caches_pipelines/cache_final`. Он содержит
`meta.pkl` с `documents`/`doc_sids` и memmap-эмбеддинги. Малый сессионный индекс
собирается из исходных BGE-векторов только для ИОР текущей выгрузки; поиск
использует cosine/IP и порог `0.7`. Не используй `cache_le_finale2`, поля
обращений или метрики СВА.

Тот же `bge_search_engine.py` является единственным поисковым модулем и
сохраняет лениво загружаемый глобальный pipeline для будущих сценариев:
FAISS + BM25 (`BM25_CHUNK=200000`) → RRF (`K=60`, вес BM25 `0.3`) → локальный
BGE reranker. Глобальный поиск не запускается автоматически при follow-up.

Пути можно переопределить:

- `IOR_RAG_CACHE_DIR` — `cache_final`;
- `IOR_BGE_MODEL_PATH` — локальный `BAAI:bge-m3`;
- `IOR_RERANKER_MODEL_PATH` — локальный `bge-reranker-v2-m3`.

## CLI

```bash
bash skills/ior-analyzer/ior_analyze.sh \
  --preset financial_consequences_ior \
  --prompt "Выгрузи финансовые последствия за прошлый месяц" \
  --session-id sess_001
```

`--prompt` обязателен и всегда содержит полный пользовательский запрос.
